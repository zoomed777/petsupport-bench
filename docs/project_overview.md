# PetSupport-Bench 项目说明（导师阅读版）

个人参赛作品｜犀牛鸟开源·混元大语言模型实战任务一｜非腾讯官方项目

## 一、项目定位

PetSupport-Bench 是一个**基于 Hy3 的宠物咨询 Agent 原型及其开放式回答评测系统**。项目在既有宠物商城客服工程基础上改造，包含两部分：一是可运行的多轮聊天应用，二是针对该场景自行定义并验证的评估方法。没有训练或微调模型，也不将系统定位为宠物医生或已上线的商业客服。

目标场景是宠物商城咨询中混杂健康描述。例如，用户询问“狗粮为什么还没到”，同时提到宠物误食。系统需要识别两类诉求，对已识别的风险优先回应，在信息不足时追问，并整理就诊准备信息，而不是只回答订单问题。

此类回复没有唯一标准答案：风险是否被回应、信息是否充分、建议是否越界、依据是否可核对、表达是否容易理解，都影响质量。因此，项目不仅展示“能够生成回答”，也研究“如何判断回答的质量，以及评估方法本身有哪些失效方式”。

## 二、当前应用的工作流程

```text
用户自然语言消息
  → 宠物身份与话题识别（不明确时先确认）
  → 当前宠物档案、本次事件、已更正事实与上下文预算
  → 意图路由、已知紧急风险检查
  → 对话内追问 / 就诊准备报告
  → 输出字段检查、实际模型调用与记忆变更记录
```

用户不需要选择“健康”“订单”等分类，也不需要预先填写档案表格。例如，先说“狗叫豆豆，3岁，今天食欲不好”，之后补充信息或更正年龄；系统在同一对话里维护有效信息。说“另一只猫叫咪咪”时会切换档案，指代有歧义时不会强行归属。

Hy3实际承担部分语义路由、对追问回复的信息提取、报告文案增强以及批量评审。并非每一轮都调用模型；明确的规则回复和追问会标注未调用Hy3。这里的Agent是有状态、有约束的领域对话应用，不是能够自主访问并操作真实商城后台的通用自治系统。

## 三、主要实现内容

| 模块 | 当前实现 | 对应代码 |
|---|---|---|
| 交互层 | 自然语言聊天、历史消息、追问、报告下载与记录查看 | `streamlit_demo.py`、`app/chat_session.py` |
| 咨询处理 | 意图识别、槽位抽取、有限知识卡片、Hy3文案增强 | `app/triage/` |
| 风险与输出约束 | 已知红旗规则、诊断/用药等输出检查 | `app/guardrails/`、`config/redflag_rules.json` |
| 记忆管理 | 按宠物与事件隔离、字段更正、结构化摘要、历史与请求预算 | `app/memory.py`、`app/chat_session.py` |
| 本机持久化 | 用户主动开启的SQLite档案与会话保存、恢复、清除 | `app/memory_store.py` |
| 开放式评测 | 七维rubric、语义Judge与规则联合、逐条输出及调用记录 | `prompts/final_judge.md`、`eval/final_judge.py`、`scripts/final_eval.py` |
| 方法验证 | 好中差排序、重复评分、伪引用/评分指令攻击验证 | `scripts/validate_final.py` |

知识库目前为8条附具体来源链接的简短转述，使用关键词匹配，不将其包装成大规模向量检索系统。记忆摘要是基于已提取事实的结构化摘要，不是LLM自由撰写的长期记忆。Token预算采用保守字节代理量，实际用量另以API返回的usage记录。

## 四、评估设计与实际结论

七个维度为风险回应、分流、信息处理、证据、安全边界、行动完整性及表达。每维有0–4分的可执行判定标准；特定风险遗漏或输出红线命中时触发总分上限。生成与评分使用同一Hy3，评分端不接收配置名称或应用自报完成项。

冻结实验使用100条作者构造样本，包含39种不同表达；其中混合意图、诱导和长文本干扰共25条。它不是100个独立真实用户，也不是兽医标注的临床数据集。

| 冻结配置 | 含义 | 有效评分 | 平均分 |
|---|---|---:|---:|
| A0 | 同一Hy3直接回复 | 100 | 83.70 |
| A3 | 规则、追问、知识卡片与Hy3增强管线 | 100 | 78.78 |

完整配置没有在总分上胜出。另构造4种场景的好、中、差及对抗输出，完成48次评审：4种场景均按好＞中＞差排序；同一输出重复评分的平均总体标准差为2.048，最不稳定样本为11.31。该结果支持这些小规模构造场景上的判别与重复性观察，不能外推为人工一致性或临床可靠性。

评测同时暴露了评估器缺陷：A0有15条输出仅因规则触发闸门，其中发现长否定句误报；A3的4条闸门来自语义Judge。因此，不能把17次与4次的差异解释为真实危险回答减少。原评分和分歧均公开，未在看到结果后修改规则以提高成绩。

## 六、完成状态与尚未覆盖的部分

当前完成了可运行应用、构造样本、评估标准与脚本、原始结果、方法验证、分析报告、演示视频及运行说明，形成可交付的参赛研究原型。应用运行所需的项目源码已提交；密钥、第三方依赖安装目录及本机私人数据不随仓库发布，详见[交付范围与未提交内容说明](submission_scope.md)。

未接入真实订单、物流、库存和人工接管；未完成云端账户隔离、跨设备记忆同步、加密存储、精确Hy3 tokenizer或大规模知识检索。复杂名字、别名、指代和纠错仍可能需要确认；风险规则存在漏检与误报。没有兽医/人工一致性或临床有效性验证。

这些是当前实现边界，不应写成“功能已经实现但代码未公开”。后续优先方向是独立校准集上的评估器改进、更多多轮难例，以及在明确隐私和授权条件下开展人工复核。

## 七、导师快速核验建议

1. 先查看本文和[交付范围说明](submission_scope.md)，明确当前入口与旧模块的区别。
2. 按[README运行说明](../README.md)启动应用；无API时可切换离线规则，不能将其视为在线模型验证。
3. 运行`python -m pytest tests/test_final_submission.py tests/test_memory.py -q`，检查当前参赛路径。旧客服集成测试不在这28项范围内。
4. 查看`results/final/`和`results/memory/`的逐条证据，而不是只看均分或成功案例。实时重跑需自行配置密钥并消耗API额度；脚本有缓存或防覆盖行为，读取已保存结果不等于重新调用模型。

项目的主要价值在于把场景化交互、可解释的工程约束与可复核评测结合起来，并公开模型与评估器自身的失败；不以堆叠功能名称或保证“零风险”作为完成标准。
